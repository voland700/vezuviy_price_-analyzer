# Архитектура

В этом документе описаны компоненты системы, потоки данных и принципы их
взаимодействия.

---

## Обзор

Analyzer — это **двухкомпонентная система**, в которой сбор данных и их
отображение разнесены:

| Этап | Компонент | Технология | Доступ к БД |
|---|---|---|---|
| 1. Сбор данных | Python-парсер `scripts/analyzer.py` | Python 3 | **запись** (TRUNCATE + INSERT) |
| 2. Отображение | Веб-приложение (этот репозиторий) | Laravel | **только чтение** |

> Принципиально важно: **Python и Laravel связаны исключительно через схему БД.**
> Между ними нет API-вызовов, очередей или общих файлов состояния. Единственный
> «контракт» — структура таблиц `suppliers`, `availables`, `unavailables`,
> `undiscovereds`, `kits`.

## Диаграмма потока данных

```
        ┌─────────────────────┐         ┌──────────────────────┐
        │  Фиды поставщиков   │         │  Фид магазина        │
        │  XML / YML (4 URL)  │         │  JSON (1 URL)        │
        └──────────┬──────────┘         └──────────┬───────────┘
                   │                               │
                   ▼                               ▼
        ┌─────────────────────────────────────────────────────┐
        │                    analyzer.py                       │
        │   fetch → parse → normalize → compare (по SKU)       │
        │   + расчёт комплектов (kits)                         │
        └──────────────────────────┬──────────────────────────┘
                                   │  TRUNCATE + batch INSERT
                                   ▼
        ┌─────────────────────────────────────────────────────┐
        │            MySQL / MariaDB  (БД `analyzer`)         │
        │  users | cache | jobs                                │
        │  suppliers | availables | unavailables |            │
        │  undiscovereds | kits                                │
        └──────────────────────────┬──────────────────────────┘
                                   ▲
                                   │  только чтение (Eloquent)
        ┌─────────────────────────────────────────────────────┐
        │                Laravel-приложение                    │
        │   Dashboard (Chart.js) · таблицы · фильтры · XLSX    │
        └─────────────────────────────────────────────────────┘
```

## Ключевая логика: классификация по SKU

Пусть `S` — множество уникальных SKU поставщиков, `M` — множество SKU магазина.
Сравнение идёт по полю **SKU**: `vendorCode` (XML поставщика) ↔ `sku` (JSON
магазина).

| Таблица | Множество | Что хранит |
|---|---|---|
| `suppliers` | все офферы `S` | полный каталог поставщиков |
| `availables` | `S ∩ M` (пересечение) | товары «и там, и там» + сравнение цен |
| `unavailables` | `M − S` (только магазин) | товары, которых нет у поставщика |
| `undiscovereds` | `S − M` (только поставщик) | товары, которых нет в магазине |
| `kits` | подмножество `M` | комплекты: сумма цен компонентов vs цена комплекта |

**Контрольные соотношения** (используются для проверки корректности прогона):

- `availables + unavailables = всего товаров магазина`
- `availables + undiscovereds = всего уникальных SKU поставщиков`

---

## Сравнение цен

Поле `info` в таблицах `availables` и `kits`:

| Условие | `info` |
|---|---|
| `supplier_price == shop_price` | `NULL` (равно) |
| `supplier_price > shop_price` | `больше` |
| `supplier_price < shop_price` | `меньше` |

## Компоненты детально

### 1. Python-парсер (`scripts/analyzer.py`)

Ответственность:

1. Загрузка XML-фидов 4 брендов-поставщиков и JSON-фида магазина по HTTP.
2. Нормализация данных (приведение типов, очистка, JSON для `pictures`/`params`).
3. Классификация товаров по SKU (см. выше).
4. Сравнение цен и расчёт комплектов (`kits`).
5. Полная перезапись таблиц (`TRUNCATE` + пакетная вставка `executemany`,
   размер чанка `BATCH_SIZE = 500`).

Параметры подключения к БД скрипт читает из `.env` приложения (секция `DB_*`),
поэтому единый источник правды для обоих компонентов.

Подробности — в [`../scripts/README.md`](../scripts/README.md).

### 2. Веб-приложение (Laravel)

Слои:

- **Маршруты** (`routes/web.php`) — все бизнес-маршруты защищены middleware
  `auth`. `/` → редирект на `/dashboard`.
- **Контроллеры** (`app/Http/Controllers/`) — по одному на раздел
  (`SupplierController`, `AvailableController`, ...). Каждый использует трейт
  `AppliesSorting` для построения запроса, валидации сортировки и формирования
  имени файла экспорта.
- **Модели** (`app/Models/`) — Eloquent-модели с `$guarded = []` (массового
  заполнения из приложения нет; данные пишет Python).
- **Экспорт** (`app/Exports/`) — классы для maatwebsite/excel, реализуют
  `FromQuery` + `WithHeadings` + `WithMapping`. Экспортируют **ту же выборку**,
  что и таблица на странице (с учётом фильтров).
- **Views** (`resources/views/`) — Blade-шаблоны: `dashboard.blade.php`,
  разделы `suppliers/`, `availables/`, `unavailables/`, `undiscovereds/`,
  `kits/`, общие `layouts/` и переиспользуемые `components/`.

Подробности — в [`WEB-INTERFACE.md`](WEB-INTERFACE.md).

## Важные архитектурные принципы

1. **Единый контракт — схема БД.** Любое изменение структуры таблиц требует
   синхронного обновления и миграций Laravel, и SQL-запросов в `analyzer.py`.
2. **Веб только читает.** Приложение не создаёт/не правит бизнес-данные — это
   снижает риск рассинхронизации с парсером.
3. **Полная перезапись, а не инкремент.** Каждый прогон парсера очищает таблицы
   и заливает актуальный срез целиком — данные всегда консистентны по
   временной метке `created_at`.
4. **Безопасная сортировка.** Сортировка по столбцам проходит через whitelist
   (`SORTABLE` в каждом контроллере), что исключает SQL-инъекции через
   `ORDER BY`.
5. **Один источник учётных данных.** `.env` Laravel используется и Laravel, и
   Python — нет дублирования паролей.

## Поток запроса пользователя (пример)

Пользователь открывает **«Есть в сайте»** и фильтрует товары с завышенной ценой:

```
GET /availables?info=more&sort=supplier_price&direction=desc
        │
        ▼
AvailableController::index()
        │  buildQuery():  Available::where('info','больше')
        │                     ->orderBy('supplier_price','desc')
        │  applySorting():  валидация 'supplier_price' по whitelist
        │  paginate(50)->withQueryString()   ← фильтры сохраняются в пагинации
        ▼
view('availables.index')  →  таблица + <x-export-button>
        │
        └─ пользователь жмёт «Экспорт»:
              GET /availables/export?info=more&sort=supplier_price&direction=desc
                    │  та же buildQuery() (без пагинации)
                    ▼
              AvailableExport::download('availables_2026-07-16_12-00-00.xlsx')
```

Ключевая идея: **один и тот же метод `buildQuery()`** формирует и таблицу, и
файл экспорта — поэтому выгрузка всегда совпадает с тем, что видит
пользователь.
