# Analyzer — скрипт парсинга и сравнения товаров поставщиков и магазина

Python-скрипт для анализа, сравнения стоимости и наличия товаров поставщиков
(XML) и товаров каталога интернет-магазина (JSON). Полученные результаты
сохраняются в базу данных MySQL/MariaDB `analyzer`.

Это **первый этап** приложения. Веб-интерфейс (Laravel) для просмотра и
фильтрации данных реализуется отдельно и читает данные из тех же таблиц БД.

## Назначение

Скрипт решает задачу синхронизации и сверки товарных каталогов:

1. Загружает данные товаров поставщиков в формате **XML** (YML / Yandex Market).
2. Загружает данные товаров каталога интернет-магазина в формате **JSON**.
3. Нормализует и обрабатывает полученные данные.
4. Сравнивает товары по полю **SKU** (`vendorCode` у поставщика ↔ `sku` в магазине).
5. Классифицирует каждый товар в одну из трёх категорий сравнения:
   - **availables** — товар есть и у поставщика, и в магазине;
   - **unavailables** — товар есть в магазине, но отсутствует у поставщика;
   - **undiscovereds** — товар есть у поставщика, но отсутствует в магазине.
6. Сравнивает цены поставщика и магазина и сохраняет результат сравнения.
7. Рассчитывает суммарную стоимость компонентов товарных **комплектов** у поставщика
   и сравнивает её с ценой комплекта в магазине.
8. Записывает все результаты в БД `analyzer`.

```
        ┌─────────────────────┐        ┌──────────────────────┐
        │   XML поставщиков   │        │   JSON магазина      │
        │ (4 бренда, по URL)  │        │   (1 URL)            │

                  │                               │
                  ▼                               ▼

        │                   analyzer.py                     │
        │  fetch → parse → normalize → compare (по SKU)     │
        └────────────────────────┬──────────────────────────┘
                                 │ TRUNCATE + batch INSERT

        ┌───────────────────────────────────────────────────┐
        │            MySQL/MariaDB  (БД analyzer)           │
        │  suppliers | availables | unavailables |          │
        │   undiscovereds | kits                            │

                                 ▲
```

Python и Laravel связаны **только через общую БД** (и опционально через

## Источники данных

### 1. XML поставщиков (формат YML)

Каждый поставщик отдаёт каталог товаров по своему URL. Структура:

```xml
<categories>
    <category id="1">Авто</category>
    <category id="2" parentId="1">Автомобильные инструменты</category>
</categories>

<offers>
    <offer id="2" available="true">
        <url>https://vezuviy.su/...</url>
        <price>18780</price>
        <currencyId>RUB</currencyId>
        <categoryId>2867</categoryId>
        <picture>https://.../img1.jpg</picture>
        <picture>https://.../img2.jpg</picture>
        <store>false</store>
        <name>Дверка ВЕЗУВИЙ каминная 224 (Антрацит)</name>
        <vendorCode>00000017469</vendorCode>
        <description>...</description>
        <param name="Цвет">антрацит</param>
        <param name="Толщина стекла">4</param>
    </offer>
</offers>
```

### 2. JSON магазина

```json
{
  "data": {
    "00000002557": {
      "id": 130,
      "name": "Везувий Легенда Ковка 12 (220)",
      "active": 1,
      "code": "4680019121888",
      "sku": "00000002557",
      "price": 46510
    }
  }
}
```

Ключ объекта `data` совпадает со значением `sku`. Поле `code` не используется.
Ключевое поле для сравнения — **`sku`** (`vendorCode` поставщика ↔ `sku` магазина).

## Логика работы скрипта

### Извлечение данных из XML-оффера поставщика

| Поле БД | Источник в XML | Преобразование |
|---|---|---|
| `name` | `<name>` | строка |
| `sku` | `<vendorCode>` | `.strip()` (очистка концевых пробелов) |
| `brand` | `brand_name` из конфига | строка |
| `category` | `<categoryId>` → название по `<categories>` | lookup по id |
| `available` | атрибут `<offer available="true/false">` | `"true"`→1, иначе 0 |
| `store` | `<store>true/false</store>` | `"true"`→1, иначе 0 |
| `url` | `<url>` | строка |
| `price` | `<price>` | целое число |
| `pictures` | все `<picture>` | JSON-массив строк |
| `description` | `<description>` | текст |
| `params` | все `<param name="...">` | JSON `[{"name","value"}, ...]` |

Пример поля `params` после преобразования:

```json
[
  {"name": "Цвет", "value": "антрацит"},
  {"name": "Толщина стекла", "value": "4"}
]
```

### Классификация по SKU

Пусть `S` — множество уникальных SKU поставщиков, `M` — множество SKU магазина.

| Таблица | Условие | Источник значений |
|---|---|---|
| `suppliers` | все офферы всех поставщиков | поставщик |
| `availables` | `S ∩ M` (пересечение) | магазин + поставщик |
| `unavailables` | `M − S` (только магазин) | магазин (`available` = 0) |
| `undiscovereds` | `S − M` (только поставщик) | поставщик |

### Сравнение цен (поле `info` таблицы `availables`)

| Условие | Значение `info` |
|---|---|
| `supplier_price == shop_price` | `NULL` |
| `supplier_price > shop_price` | `больше` |
| `supplier_price < shop_price` | `меньше` |

### Комплекты товаров (таблица `kits`)

Поставщик предлагает товары по отдельности, а магазин продаёт их комплектом
(например, сковорода + крышка). Для расчёта в начале `analyzer.py` задан список
`KITS_DATA`, где каждый элемент описывает комплект магазина:

| Поле `KITS_DATA` | Назначение |
|---|---|
| `id` | `id` товара-комплекта в каталоге магазина (поле `id` JSON-фида) |
| `name` | название комплекта в каталоге магазина |
| `code_first` | SKU первого компонента (`<vendorCode>` поставщика) |
| `code_second` | SKU второго компонента (`<vendorCode>` поставщика) |

Логика расчёта для каждого комплекта:

1. `shop_price` — цена комплекта берётся из JSON-фида магазина по `id`
   (строится индекс товаров магазина по полю `id`).
2. `price_1`, `price_2` — цены компонентов берутся из данных поставщика по их SKU.
3. `supplier_price = price_1 + price_2` — суммарная стоимость компонентов.
4. `info` — результат сравнения `supplier_price` и `shop_price` по тем же
   правилам, что и для `availables` (`NULL` / `больше` / `меньше`).

Если товар-комплект не найден в каталоге магазина по `id` или хотя бы один из
компонентных SKU отсутствует у поставщика, комплект **пропускается** с записью
`[WARNING]` в лог (не прерывая общий прогон).

### Оптимизация записи в БД

- Перед загрузкой все таблицы очищаются (`TRUNCATE`, с временным отключением
  `FOREIGN_KEY_CHECKS`).
- Вставка выполняется пакетами через `executemany()` с размером чанка `BATCH_SIZE`
  (по умолчанию 500 строк).
- Все поля `created_at` / `updated_at` заполняются временем прогона.

### Устойчивость к ошибкам

- Каждый оффер парсится в блоке `try/except`: битый/некорректный оффер
  пропускается с записью предупреждения в лог, не прерывая общий прогон.
- Каждый поставщик обрабатывается независимо.

### Контрольная сверка количества строк

- `availables + unavailables = всего товаров магазина`
  (1356 + 167 = **1523**).
- `availables + undiscovereds = всего уникальных SKU поставщиков`
  (1356 + 1266 = **2622**).
- `kits ≤ len(KITS_DATA)` — количество строк в `kits` равно числу комплектов, у
  которых найдены и товар-комплект в магазине, и оба компонента у поставщика
  (пропущенные комплекты отмечаются в логе уровнем `WARNING`).

## Журнал работы и диагностика

Скрипт пишет прогресс в `stdout` в формате `logging` (уровень `INFO`):

- `GET <url>` — запрос к источнику данных;
- `<Бренд>: N offers` — количество распарсенных офферов поставщика;
- `Сравнение: ...` — итоги классификации;
- `<Таблица>: вставлено N строк` — результат пакетной вставки;
- `[WARNING] [<Бренд>] пропуск offer id=...` — пропущенный некорректный оффер.

## Проверка результатов

Быстрые SQL-проверки содержимого БД:

```sql
-- распределение результата сравнения цен
SELECT IFNULL(info, 'равно') AS info, COUNT(*)
FROM availables
GROUP BY info;

-- товары, у которых цена поставщика выше цены магазина
SELECT shop_id, sku, shop_price, supplier_price, info
FROM availables
WHERE info = 'больше';

-- комплекты: расхождение суммарной стоимости компонентов с ценой комплекта
SELECT shop_id, name, price_1, price_2, supplier_price, shop_price, info
FROM kits
WHERE info IS NOT NULL;

-- комплекты: распределение результатов сравнения
SELECT IFNULL(info, 'равно') AS info, COUNT(*)
FROM kits
GROUP BY info;

-- пример характеристик товара в формате JSON
SELECT name, JSON_PRETTY(params) AS params
FROM suppliers
WHERE sku = '00000017469';

-- количество изображений у товара
SELECT sku, JSON_LENGTH(pictures) AS pic_count
FROM suppliers
WHERE sku = '00000017469';

-- новинки поставщика, отсутствующие в магазине
SELECT sku, name, brand, price
FROM undiscovereds
ORDER BY brand, price DESC;
```

## Возможные проблемы и решения

| Симптом | Причина | Решение |
|---|---|---|
| `Data too long for column 'url'` | URL длиннее размера столбца | столбцы `url` расширены до `VARCHAR(1000)` в `suppliers` и `undiscovereds` |
| `DB_* не найдены в .env` | скрипт не нашёл `.env` | проверьте путь к `.env` (`PROJECT_ROOT/.env`), наличие секции `DB_*` |
| `pymysql` / `ModuleNotFoundError` | не установлены зависимости | `sudo apt-get install python3-pymysql` |
| `Connection refused` / доступ к БД | неверные учётные данные или БД недоступна | проверьте `DB_*` в `.env` и статус службы MySQL |
| `HTTPError 404/500` при загрузке фида | временная недоступность источника | источник данных временно недоступен; повторите позже |
| Расхождение цен только в нескольких позициях | свойство исходных данных | фид магазина может формироваться на основе цен поставщика — это не ошибка скрипта |

## Связь с Laravel (этап 2)

Таблицы `suppliers`, `availables`, `unavailables`, `undiscovereds`, `kits`
создаются миграциями Laravel в `/var/www/dm.pechnik.su/database/migrations/` и
описаны моделями в `app/Models/`. Будущий веб-интерфейс работает с теми же таблицами
на чтение, поэтому координация между Python и Laravel осуществляется
исключительно через схему БД: при изменении структуры таблиц необходимо
обновлять и миграции Laravel, и скрипт `analyzer.py`.
